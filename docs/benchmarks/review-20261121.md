# What the fast-silicon benchmarks support

The project’s strongest results are bulk retrieval and strict Gemma extraction. Its three retrieval packages finished the scored jobs faster than stock MLX on both Macs. On the 24 GB M5, the repaired Gemma default returned 150 schema-valid documents and scored **0.945 field F1**. On four-way preference questions, even correctly loaded Laya models picked the preferred answer only 29–32% of the time. The downstream extraction tests support optional review prioritization and give no quality benefit for automatic verification. [Retrieval results][retrieval] · [Gemma experiment][gemma] · [Decision results][decisions]

The review covers seven package READMEs, the benchmark guide, independent reader and technical reviews, and the downstream extraction checks. The main comparison used a 48 GB M4 Pro on macOS 26.6 and a 24 GB base M5 on 27.2.1. The separate scanned-document experiment used a base M5 on 26.2. All implementations ran locally. The project packages control batching, caching and processor selection. Stock MLX uses the named public library. Public Core ML exports come from the named publishers. Apple CoreAI runs `.aimodel` files. [Implementations and hardware][implementations] · [Evidence locations](#evidence-locations)

## Major findings and repairs

| Finding | Change and verification |
| --- | --- |
| Gemma produced valid JSON with wrong values | Restored the full checkpoint output vocabulary and made a single space after each key’s colon part of the strict grammar. On 150 M5 documents, full-vocabulary field F1 rose from **0.766** with minified JSON to **0.945** with the new layout. The number of documents containing a field equal to `": "` fell from 73 to zero. The same engine without constraints scored 0.918 with 145 valid outputs. On 48 disjoint M4 Pro documents both settings scored 0.926 and produced 48 valid outputs. [Paired scores and token trace][gemma] |
| Laya’s stock baseline skipped 170 pretrained weights | The loader now requires every encoder weight. Its probabilities and option rankings were checked against a reference model, including a 512-token input. A full stock rerun scored **0.5014 on M5 and 0.5021 on M4 Pro**. The old 0.2757 and 0.2986 rows are invalid. Project Laya’s best evidence in the downstream application remains helping a human choose what to review. [Corrected runs][decisions] · [Downstream decision tests](#decision-scoring) |
| PPLX discarded the caller’s token limit during routing | Prepared token IDs and chunk boundaries now reach the selected processor. Tests on the actual GPU, Neural Engine and both mixed modes verified the limit, chunk order and fully truncated chunks against physically truncated inputs. Coverage now counts every intended retrieval query. The historical 150/325 run fails coverage and the windowed run reaches 325/325. [PPLX implementation and evidence][pplx-guide] · [Scored runs][doc-runs] |
| Stock Kev loaded an extra scoring model and earlier rates timed a partial workload | The revised baseline uses a tokenizer-only formatter and one scorer. All **7,650** option sequences and decision positions matched across the 1,400 questions. The cache benchmark now explicitly disables reuse in its plain arm and scores actual passage/question pairs through the decision head. Stock finished first on M5, project Kev on M4 Pro. [Matched results][decisions] |
| An uncertain quality result could pass as “lossless” | The comparison now uses a fixed application tolerance and a paired 95% confidence interval. It reports unresolved quality when the interval spans the tolerance. M5 PPLX delivered 4.41× the score per second, with a ranking-score difference of +0.00083 and an interval from −0.00362 to +0.00528. At the default tolerance of 0.003, equivalence remains unresolved. GPT-OSS also has unresolved quality, and two repeat loops independently fail its promotion check. [Comparison rule][gate] · [Item scores and recalculated outcomes][doc-runs] |
| Draft, compilation, precision and training claims overstated what ran | The guides now give host-specific output agreement for the Gemma draft assistant, loop counts for both Qwen 4B precision settings, actual training inputs and token counts, and measured BGE vectors from both compiler modes on both Macs. ## Which implementation earns its place

### Search and indexing

The encoder timings below start with a loaded model. FP16 uses 16-bit floating-point values. INT8 uses 8-bit integers.

| Model | Where the project helps | Where another implementation helps or evidence is missing |
| --- | --- | --- |
| **BGE-small** | For short English text, the project finished 325 M5 retrieval queries in **11.8 s**, against **60.0 s** for sidekickd FP16 Core ML. Mean ranking scores were 0.4737 and 0.4739. One warm 24-token query took 0.79 vs 1.61 ms on M5 and 0.49 vs 1.70 ms on M4 Pro. Splitting corpus work between the GPU and ANE also beat the project’s own GPU-only path on both hosts. | Sidekickd used **0.54 GB** in the M5 scored run against **1.54 GB** for the project. Stock MLX scored slightly higher at 0.4774. A different public export from `michaeljelly` returned non-finite or poorly matching vectors in spot checks. Use the named, checked export for a memory comparison. [Scores and memory][coreml] · [Warm probes][warm] |
| **EmbeddingGemma-2** | For bulk indexing on M5, the project processed **48,803 tokens/s** across 2,000 pretokenized documents, against **14,945** for OpenInfinity INT8 and **14,187** for FluidInference FP16. The project reads up to 2,048 tokens per passage. The public Core ML exports read 512. On long passages their ranking scores were 0.569, 0.518 and 0.516 respectively. | For an always-warm query service, OpenInfinity took **2.59 ms** against the project’s **2.58 ms**. In the separate scored run it used **0.84 GB**, FluidInference used **1.38 GB**, and the project used **3.43 GB**. Short-passage scores were within 0.002. With matched 512-token input on M4 Pro, all three scored 0.516–0.518 for returning the whole passage and recovered 33.6% of labeled characters from the text they actually saw. Raising only the project limit to 2,048 raised visible character recovery to 90.3% and encoding time from 2.39 to 14.58 s. [Matched legal passage scores][legal-512] [Input audit and scores][coreml] · [Matched timing][warm] |
| **PPLX contextual 0.6B** | On 175 legal questions, including neighboring text raised the project’s passage-ranking score from **0.359 to 0.703** and coverage of relevant characters in the first ten results from **68.4% to 87.9%**. Stock contextual MLX also scored 0.703. The full 325-query text job took **136.5 vs 601.5 s** on M5 and **167.3 vs 723.1 s** on M4 Pro. | Public `pplx-context-mlx` led on 32 short M5 queries at **917 vs 871 queries/s** for the fastest project mode. Upstream also demonstrated direct page-image inputs and a 113,281-token context on a different system. The project demonstrated 32,768 synthetic tokens, and the scored legal test used 4,096-token windows. Choose the path that matches the real input. [Retrieval results][retrieval] · [PPLX guide][pplx-guide] · [Upstream and archived probes](#evidence-locations) |

**What explains the indexing gains?** Batching and scheduling have direct support. In PPLX’s public adapter, 2.14 million real passage tokens became 5.37 million positions after padding in document order. Grouping the same passages by length would require 2.18 million positions. On a 384-passage M4 Pro sample, sorting stock’s inputs by length cut encoding from **20.65 to 13.34 s** with the same batch size. All 24 labeled queries returned the same ordered top ten. On eight long windows, the shipped single-window loop took 4.39 s and sorted two-window batches took 4.36 s. These matched measurements identify a contributor to the full-job gap. [Stock padding experiment][padding] In EmbeddingGemma, Apple CoreAI BF16 processed 879,616 padded positions for 551,889 real tokens. The whole-job timings include all these differences. Packing short inputs increased throughput in the public Core ML EmbeddingGemma exports by only 3.5–4.6% on the mixed corpus. Their compute plans left the packed function’s placement unclassified. Apple CoreAI BF16’s full-run memory reading was invalid. The 3.04 GB replacement figure comes from a separate five-text check. [Public adapters][public-adapters] · [Corpus timings][warm] · [Memory evidence][coreml]

**When does custom Metal help?** On 7,974 scanned-text passages, widening the project’s fused BGE matrix tiles cut elapsed time from **9.54 to 8.53 s**. For EmbeddingGemma, replacing plain custom matrix multiplies with built-in MLX cut **54.28 to 46.20 s**, while retaining the project’s batching and fused operations. Both preserved first-place and top-five passage hits across 64 labeled queries. A PPLX change that combined two projections produced identical vectors but took 12.05 vs 11.96 s on 384 passages. These trials included tokenization, reading Parquet and writing vectors. [Controlled kernel experiments][kernels]

### Decision scoring

**Laya-Typed-421M.** Three different decisions had three different outcomes.

| Use | What happened | Decision |
| --- | --- | --- |
| Accept or reject an extracted record | Adding Laya on M5 increased runtime from **93.31 to 160.71 s**. Held-out extraction quality stayed at **89.38**. A separate run raised the flag count from **16 to 23** while extraction scores stayed flat. On 48 documents, Laya classified document kind correctly on 22, a simple word-frequency classifier on 39, and the existing Gemma pipeline on 42. | Keep the downstream extraction pilot’s `--atomic-verifier` CLI flag off by default. Use the pipeline’s field checks and measured routing policy for automatic decisions. [Pipeline comparison and flag counts][decisions] · [Classification trial](#evidence-locations) |
| Choose which extractions a person reviews | The 48-document pilot contained 12 known defective extractions. Among the first ten sent to review, rules alone surfaced **4**, Laya alone **5**, and rules plus Laya **7**. | Combining Laya with rules is worth testing at a fixed review budget. The three additional defects surfaced by the combination are the useful outcome. [Review-queue trial](#evidence-locations) |
| Pick a training reward or best answer | On 250 four-way choices, project Laya chose the preferred answer **73 times (29.2%)**, NMTZ **76 times (30.4%)** and corrected stock MLX **79 times (31.6%)**. Random choice averages **25%**. On other public tasks project Laya achieved 63.8% faithfulness accuracy and 45.6% intent accuracy. | Use labeled outcomes or a separately validated judge for training rewards. NMTZ’s additional action/abstain head needs its own evaluation. [Public option-scoring runs][coreml] |

These results concern the **typed** Laya checkpoint. On the same 48 documents the general and multilingual checkpoints flagged 46 and 43 documents respectively, compared with 17 for typed Laya. Those figures measure review volume. [Checkpoint trials](#evidence-locations)

On the 1,400-item mixed workload, stock MLX Laya was fastest on M5 (**73.9 s**, compared with NMTZ’s 88.4 and the project’s 114.8). NMTZ was fastest on M4 Pro (**92.0 s**, compared with 121.3 and 130.7 for the project and stock). The project scored 0.5050 on both Macs and used about 1 GB. NMTZ scored 0.4993 and used 2.73–2.94 GB. Stock scored 0.5014–0.5021 and used 1.88–2.00 GB. The ahmedandaloes export in Apple CoreAI took 940.7 s on M5. These timings answer how soon a particular score is available. Its fitness to make a decision depends on that decision’s labeled outcomes. [Corrected stock results][decisions] · [Core ML and CoreAI comparisons][coreml]

**Kev-0.8B.** On M5, stock MLX completed the 1,400 questions in **145.5 s** and project Kev in **167.2 s**. On M4 Pro, project Kev finished in **215.2 s** and stock in **225.3 s**. FluidInference took 321.7 and 435.4 s respectively. Scores fell between 0.521 and 0.525. FluidInference reached 187 questions/s on M5 for eight questions sharing one 14-token passage and 21/s for one question. In the extraction pilot, rules plus Kev surfaced 8 of 12 defects in the first ten reviews, but adding Kev as a second stage later reduced cross-validated ranking quality on both Macs. Document reuse and task accuracy both affect the choice. [Single-model baseline and measured prefix reuse][decisions] · [Core ML results][coreml] · [Downstream evaluation][decisions]

## What the remaining evidence would change

- **Reviewer time.** A larger prospectively labeled extraction sample can test whether rules plus Laya surface more actual defects at the same human review budget. Automatic acceptance and training rewards need their own accuracy measures.
- **Serving and capacity.** Measure first useful response from comparable cold caches. A direct GPT-OSS capacity comparison still needs identical prompts, reasoning settings, batch, output limits and finish accounting. A larger tool-call evaluation is more valuable than another JSON parse count.
- **Training.** Time prefix reuse on the same supervised answers and optimizer updates, then measure held-out loss. A completed 24 GB training run would settle the remaining sizing recommendation.
- **Quality gates.** Report valid versus intended counts, the score on the full set, elapsed time, memory, and repeat loops. A wider paired interval means greater uncertainty. The fixed tolerance makes that uncertainty visible. [Scoring method][gate] · [Recorded outcomes][doc-runs]
